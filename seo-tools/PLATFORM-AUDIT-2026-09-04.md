# Platform audit — before the v4 "SEO command center" rebuild (4 Sep 2026)

## 1. Current architecture (verified by inspection, not guessed)

- **No framework, no server, no database.** The dashboard is ~17 static HTML pages
  generated by `seo-tools/daily/generate_v3.py` (Python, single file ~1,900 lines) and
  deployed by `git push` to the `dashboard` branch; Vercel serves the branch as static
  files. All interactivity is inline vanilla JS. Styling is one inlined stylesheet
  (`_styles.html`, currently the "Organic" hand-off design).
- **Data pipeline** (run on demand — "update the dashboard" — not scheduled):
  `crawler.py` (BFS crawl, 11 sites) → `build_findings.py` (technical defects) →
  `fetch_dash_data.py` (GSC daily clicks/impressions 90d + DataForSEO backlinks
  summary) → `refresh_kt_positions.py` (live SERP probes for 64 strategic targets,
  per-keyword country overrides for diaspora terms) → `build_content.py` (coverage/gap
  engine with cannibalization guards) → `history.py` (authority/rank time series) →
  `generate_v3.py` → deploy → snapshot promote.
- **State** = JSON files committed to `seo-tools/daily/` (dash_data, keyword_targets,
  semrush, content, findings, history, goals, links_progress, checkbox_state,
  prev/cur_snapshot). Git IS the database.
- **Integrations**: GSC service account (all 11 sc-domain properties except the new
  rodaktv.com); DataForSEO REST via `dash/.env`; Semrush via MCP connector (values
  cached in `semrush.json`, owner-verified); no GA4 on any site.
- **Sales**: separate apps owned by the sales session (`sales.html`, `clients.html`,
  `replies.html`) on the same origin. `sales.html` persists to localStorage
  (`iptv_sales_v1`, `iptv_payouts_v1`) and now also syncs via **Firebase Firestore**.
  Data model: per-sale record with site id, plan months, price EUR, panel cost,
  7.5% card fee, status (paid/activated/renewed/expired). No organic attribution.

## 2. Data sources: live vs cached vs manual

| Source | Freshness | Notes |
|---|---|---|
| Crawl/technical | live each audit | full BFS, zero-defect state across 10/11 sites |
| GSC clicks/impr | live each audit (2-day lag) | daily, site level only before v4 |
| Strategic ranks | live each audit | DataForSEO SERP probes, 64 targets |
| DataForSEO authority | live each audit | spf/ifo/rodak currently have no index rows |
| Semrush | cached at last MCP pull | owner-verified index; clearly dated |
| Sales/revenue | browser-local + Firestore | NOT readable by the generator; readable client-side |
| Volumes | cached (DFS, per-market) | refreshed occasionally |

## 3. UX problems (current)

- Site-chip row + top-nav mixes 11 sites with 8 sections; no grouping by intent.
- Executive questions (growing? declining? why? what next?) require reading prose
  narratives; deltas exist only for clicks and rank movers.
- "Keywords" shown from three different indexes without labels in some tiles.
- No period selector, no previous-period comparison, no query/page-level analytics.
- Long explanatory text visible by default on site pages.
- Alerts unranked (crit/warn only), no severity discipline.
- Links page centred on placement-checklist completion, not quality/impact.

## 4. SEO analytics gaps

- No query/page/device/country dimensions stored (fixed in v4: `fetch_gsc_details.py`).
- No CTR-vs-position expectation model, no striking-distance surfacing.
- No indexation layer (fixed in v4: `inspect_urls.py`, priority URLs only).
- No content winners/losers/decay views.
- No opportunity scoring.

## 5. Data consistency issues found

- Site registry duplicated in 4 places (generator maps, sitecards CONFIG, sales.html
  SITES list, briefs). v4 keeps `_sites.py` + generator maps as canonical; sales app
  list is owned by the sales session (do not touch) — site ids are mapped at read time.
- Sales site ids differ from domains (e.g. `primeiptv`, `other`) — mapped explicitly.
- DataForSEO vs Semrush counts differ by design — never merged in v4, always labeled.

## 6. Constraints that shape the target architecture

- Static hosting only (no server, no cron, ephemeral container) → interactivity must
  be client-side; period filters/comparisons run on embedded JSON; historical depth
  lives in committed JSON state.
- Sales data only exists in the browser/Firestore → revenue KPIs are computed
  client-side from localStorage on the same origin, labeled **total sales, not
  organic-attributed**. True organic attribution needs GA4 or UTM-tagged flows: not
  installed today, documented as a setup state, never faked.
- URL Inspection quota (2k/day/property) → inspect only money + strategic + new pages.

## 7. What ships in v4 (implemented this pass)

1. Deep GSC layer: 28d-vs-28d query/page tables (top 250), device/country, 7/28/90d
   totals with complete-period comparisons (`gsc_details.json`).
2. Indexation layer for priority URLs (`indexation.json`).
3. New design system: light neutral, white cards, 1px borders, near-black text, one
   accent, Inter; density over decoration; no giant type, no icon noise.
4. New shell: sidebar IA (Portfolio / Business / System), site selector dropdown,
   per-source freshness in the header, one audit stamp.
5. Overview = executive control center: KPI row (each with source + delta + spark),
   performance chart (clicks/impressions, previous-period ghost), What Changed feed
   (magnitude + affected page/query + hypothesis-labeled causes), severity-capped
   alerts, top opportunities.
6. Performance page: query table (winners/losers/new/lost/position bands/low-CTR/
   strategic filters, Δ columns, volume where known), page table, device/country split.
7. Rankings page: three labeled datasets (strategic probes / DFS / Semrush), shown
   separately with their own trends; disagreements surfaced, never merged.
8. Content page: winners/losers/decay/new + per-page state classification.
9. Technical page: crawl categories + indexation results; health = checks passed /
   checks run (formula shown); CWV/PSI shown as a not-yet-integrated setup state.
10. Authority page: labeled DFS/Semrush metrics, rd velocity from history, risk panel
    (spam-jump rule), links-to-strategic-pages; the placement checklist demoted to an
    operational drawer, no longer a KPI.
11. Opportunities page: transparent additive score (volume band + proximity + intent +
    CTR upside + site phase), each card = what/why/upside/action/site/page/query/source.
12. Work page: engine preserved verbatim (prompts, copy buttons); presentation adds
    priority/category/effort chips.
13. Site pages: header + KPI row + sections; strategy prose collapsed into a
    "Strategy" panel.
14. Sales tile on Overview: reads `iptv_sales_v1` client-side (same origin), renders
    total sales/revenue with an explicit "not organic-attributed" label; "no data"
    state when localStorage is empty on this device.
15. Old routes preserved: /trends → Performance, /links → Authority, /plan → Overview
    (redirect stubs), /today stays as Work.

## 8. Risks

- Big presentation change in one deploy → mitigated: engines untouched, v3 page
  builders retained in-file (new builders override), git revert = instant rollback.
- Client-side revenue depends on the owner's browser holding sales data — rendered
  as an honest empty state elsewhere.
- GSC 2-day lag means "28d" windows end 3 days ago — ranges are printed on the UI.
- rodaktv.com not yet in GSC → all its GSC-derived modules show setup states.

## 9. Metrics that cannot currently be produced reliably (rendered as setup states)

- Organic-attributed sales/revenue/conversion rate (needs GA4 or UTM discipline).
- Core Web Vitals field data (needs CrUX/PSI integration + API key).
- Publication dates for old content (not tracked at publish time; sitemap lastmod
  unreliable) — new-content tracking starts from crawl first-seen going forward.
- New/lost referring-domain counts from DataForSEO timeseries (extra API cost) —
  v4 derives velocity from our own audit history instead.
